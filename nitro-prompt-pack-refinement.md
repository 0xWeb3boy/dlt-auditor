## 1. Repo Context Summary

- Architecture summary: Nitro is an Arbitrum L2 stack built around Go-based transaction admission and sequencing (`arbnode`, `execution/gethexec`, `arbos`), validator and dispute logic (`staker`, `bold`, `validator`-adjacent paths), data-availability and feed infrastructure (`broadcastclient`, `relay`, `daprovider`), and proof/runtime machinery spanning Go and Rust/WASM (`arbos/programs`, `arbitrator`, `crates`, machine loaders).
- Trust boundaries: L1 parent-chain data into inbox and delayed-message trackers; operator config into node startup, validator startup, relay/feed wiring, and verifier selection; sequencer and express-lane ingress into privileged transaction ordering; DA/feed payloads and signatures into broadcast or provider servers; validator/challenge metadata into machine selection, proof generation, and assertion confirmation; persisted recovery state into MEL, staker, and validator restarts.
- High-risk entrypoint categories: transaction admission and sequencing; block production and replay; validator and challenge startup; proof generation and state-provider queries; DA provider RPC and streaming; feed handshake and relay startup; MEL extraction, recovery, validation, and pruning; runtime activation and stack-recovery paths.
- State-machine or lifecycle patterns that matter: delayed-message extraction versus validation versus sequencing; assertion and challenge-edge lifecycle in BOLD; round-scoped express-lane control transfer; retryable user transaction plus auto-redeem groups; validator startup and machine/artifact selection; finalized versus safe versus local-read progress across recovery and cleanup logic.
