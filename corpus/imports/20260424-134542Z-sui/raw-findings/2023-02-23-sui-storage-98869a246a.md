# Summary

The evidence supports a consensus hardening change around Narwhal certificate insertion and equivocation handling. The patch makes DAG insertion fallible, adds a `CertificateEquivocation` error, and updates Bullshark to propagate insertion errors while separately representing the below-commit-round non-insertion case. The evidence does not prove a concrete exploit path or that the old behavior could finalize conflicting commits, so a confirmed vulnerability claim is too strong.

## Observed Patch Facts

1. In `narwhal/consensus/src/consensus.rs`, the patch replaces `return false;` with `return Ok(false);`.

2. In `narwhal/consensus/src/lib.rs`, the patch replaces `#[derive(Clone, Debug, Error)]` with `#[derive(Clone, Debug, Error, PartialEq)]`.

3. In `narwhal/consensus/src/bullshark.rs`, the patch replaces `if !state.try_insert(&certificate) {` with `if !state.try_insert(&certificate)? {`.

## Before/After Behavior

Before the patch, certificate insertion into the DAG returned a boolean, and Bullshark treated `false` as a generic no-op. The same boolean covered at least the below-commit-round case and failed insertion due to an existing entry. After the patch, insertion returns `Result<bool, ConsensusError>`, below-commit certificates return `Ok(false)`, and insertion errors can be propagated through Bullshark. Recovery also treats DAG reconstruction as fallible.

# Root Cause

The prior API collapsed multiple certificate insertion outcomes into a boolean, making it hard for callers to distinguish benign ignored certificates from invariant violations such as conflicting certificates for the same origin and round.

## Walkthrough

1. A certificate reaches Bullshark `process_certificate`.

2. The code attempts to add the certificate to `ConsensusState` through the DAG insertion path.

3. Certificates at or below the origin's committed round remain a benign non-insertion and now return `Ok(false)`.

4. The insertion path now has access to an existing certificate for the same round and origin when `HashMap::insert` replaces an entry.

5. The patch introduces `ConsensusError::CertificateEquivocation` and changes insertion to return `Result<bool, ConsensusError>`.

6. Bullshark now uses `state.try_insert(&certificate)?`, so insertion errors are no longer flattened into a no-op.

7. The new `Outcome` type distinguishes normal processing outcomes from error propagation.

# Fix Pattern

Replace ambiguous boolean status with a fallible result and explicit outcome enum so callers can separate benign non-insertion from consensus-invariant errors.

## How It Was Fixed

The patch changed certificate DAG insertion to return `Result<bool, ConsensusError>`, added `ConsensusError::CertificateEquivocation`, introduced processing `Outcome` variants, updated Bullshark to propagate insertion errors with `?`, and made DAG recovery handle fallible reconstruction.

# Why It Matters

1. Equivocation handling is security-relevant in a consensus protocol.

2. Ambiguous no-op handling can hide important consensus-state anomalies.

3. The patch improves enforcement and observability of the one-certificate-per-origin-per-round invariant.
