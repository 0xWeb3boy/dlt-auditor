# Summary

The patch fixes a concrete race between certificate execution and authority reconfiguration by adding an execution-epoch RwLock, requiring certificate execution to hold a read guard for the matching epoch, and requiring reconfiguration to hold a write guard while reverting uncommitted epoch transactions and advancing epoch state. The evidence supports a concurrency/state-consistency fix in a security-sensitive validator path, but it does not establish an exploitable vulnerability, asset loss, authorization bypass, or actual consensus failure. Treat as unclear security relevance rather than a validated security fix.

## Before/After Behavior

Before the change, the provided evidence shows certificate processing performed already-executed and epoch checks without a shared execution/reconfiguration lock, and reconfiguration reverted uncommitted epoch transactions and reopened epoch state without holding such a lock. After the change, AuthorityStore has an execution epoch RwLock; process_certificate obtains a read guard through execution_lock_for_certificate, which only succeeds when the certificate epoch matches the current execution epoch; and reconfigure obtains the corresponding write guard while reverting old-epoch transactions, updating recovery/epoch DB state, and then advancing the execution epoch.

# Root Cause

A missing synchronization boundary between certificate execution and epoch reconfiguration allowed those code paths to overlap around rollback and epoch-state transition. The provided evidence supports this as a race condition, but not as a proven vulnerability root cause.

## Walkthrough

1. AuthorityStore gains an execution_lock storing the current execution epoch.

2. Certificate processing now calls execution_lock_for_certificate before continuing with epoch-sensitive execution work.

3. execution_lock_for_certificate acquires a read lock and checks that the locked execution epoch equals certificate.epoch().

4. If the epochs do not match, the helper returns SuiError::WrongEpoch.

5. Reconfiguration now acquires the execution write lock before reverting uncommitted epoch transactions.

6. Holding the write lock prevents concurrent certificate executions from holding read guards during the rollback/reconfiguration section.

7. After rollback and epoch DB reopening, reconfiguration writes the new epoch into the execution lock.

8. The commit message states the intended behavior: no transaction executes in parallel with revert, and old-epoch scheduled transactions are rejected after the epoch change.

# Fix Pattern

Add an explicit read/write concurrency guard around epoch-sensitive execution and reconfiguration, and validate certificate epoch against the guarded execution epoch before proceeding.

## How It Was Fixed

The patch adds execution_lock: RwLock<EpochId> to AuthorityStore, adds read/write guard helpers, makes certificate processing acquire a read guard only when the certificate epoch matches the current execution epoch, and makes reconfiguration acquire the write guard while reverting uncommitted transactions and advancing epoch state.

# Why It Matters

1. Prevents overlap between transaction execution and reconfiguration rollback in the shown authority path.

2. Keeps certificate epoch checks tied to a guarded execution epoch value.

3. Rejects old-epoch scheduled work after the execution epoch advances.

4. Security impact is plausible because this is validator epoch/state logic, but not proven by the supplied evidence.
