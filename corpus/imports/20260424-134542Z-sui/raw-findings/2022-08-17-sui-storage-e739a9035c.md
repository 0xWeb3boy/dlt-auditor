The patch allows online retry of interrupted transactions, but moves retry accounting into the WAL begin path and rejects retries above `MAX_TX_RECOVERY_RETRY`. The evidence supports security-relevant resource-control hardening against poison-pill or crash-loop style retries, but not a confirmed exploitable vulnerability.

## Before/After Behavior

Before, a transaction digest already present in the WAL caused `begin_tx` to return `None`, and the authority rejected online processing with an offline-retry error. Retry counting was tied to the offline recoverable-transaction pop path. After, `begin_tx` returns a guard directly, increments persisted retry count when the digest is already logged, refuses to return a guard if that accounting fails, and `AuthorityStore::acquire_tx_guard` rejects retries above the configured limit.

# Root Cause

Retry accounting was not in the common path that grants a transaction guard. Once online retry is allowed, granting execution without durable retry accounting would permit repeated recovery attempts for a transaction left in the WAL.

## Walkthrough

1. A certified transaction reaches `AuthorityStore::acquire_tx_guard`, which asks the WAL to begin processing for its digest.

2. Previously, if the digest was already in the WAL log, `begin_tx` returned `Ok(None)` and online execution did not proceed.

3. The removed comments explicitly described a possible DoS channel if clients could repeatedly retry transactions that always failed there.

4. The patch changes `begin_tx` to increment retry count for an already logged digest before returning a guard.

5. If retry count persistence fails, the WAL refuses to return a guard to avoid an unaccounted retry path.

6. The authority checks `guard.retry_num()` and rejects attempts above `MAX_TX_RECOVERY_RETRY`, with comments describing a possible poison pill.

7. The offline recovery pop path now only returns a digest, leaving retry accounting to the common begin path.

8. Object-version retention comments were updated to explain that partially executed transactions may need old input versions for retry, but the comment change is supporting context rather than the root cause.

# Fix Pattern

Centralize retry accounting in the guarded transaction-begin path and enforce a maximum retry limit before transaction execution continues.

## How It Was Fixed

`DBWriteAheadLog::begin_tx` now returns `DBTxGuard` instead of `Option<DBTxGuard>`. For digests already present in the WAL, it increments the retry count and only returns a guard if that succeeds. `AuthorityStore::acquire_tx_guard` checks the guard retry number and rejects attempts above `MAX_TX_RECOVERY_RETRY`. Retry counting was removed from `pop_one_tx` so online and offline recovery share the same accounting path.

# Why It Matters

1. Bounds repeated recovery attempts for interrupted or failed transactions.

2. Prevents guard issuance when retry accounting cannot be persisted.

3. Addresses explicitly documented poison-pill and crash-loop concerns.

4. Does not prove attacker triggerability or network-wide impact from the provided evidence.
