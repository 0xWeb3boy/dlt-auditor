# Summary

This is a confirmed availability/liveness security fix in the checkpoint-consensus path. The commit describes a malicious client delivery pattern where a validator can receive and retain a certificate but never submit it because only a randomized subset of validators was responsible for submission. The patch changes submission from exclusive selected-submitters to deterministic staggered eventual submission by every validator.

## Before/After Behavior

Before the patch, only a randomized stake-threshold subset of validators submitted a given transaction certificate to consensus, while other validators could still hold the certificate and wait for consensus processing. A malicious user could send the certificate only to non-submitters, leaving them waiting indefinitely. After the patch, each validator computes a deterministic position from the transaction digest and committee ordering, waits for a position-based delay, and submits locally if the transaction has not already appeared in consensus.

# Root Cause

The root cause was a liveness invariant mismatch: validators outside the randomized submitter subset could be required to wait for consensus visibility of a certificate they held, but had no eventual local submission responsibility if the certificate was not sent to selected submitters or propagated by another mechanism.

## Walkthrough

1. A malicious user can obtain a transaction certificate for an owned-object transaction and selectively deliver it to validators.

2. A receiving validator can sign effects and keep the certificate in pending_certificates for end-of-epoch guarantees.

3. Before the fix, submission to consensus was limited to a randomized subset of validators selected by shuffled committee stake.

4. If the certificate was delivered only to a validator outside that subset, the validator could wait for consensus processing without submitting the certificate itself.

5. The commit states there was no other gossip mechanism that would guarantee submission in this scenario.

6. At epoch boundaries, such pending certificates could prevent validators from sending end-of-epoch progress messages.

7. Repeating the trick across validators could reduce the number of validators able to make progress below the required threshold, causing denial of service.

8. The fix gives every validator a deterministic stake-aware position for the transaction and derives a submission delay from that position.

9. submit_and_wait now races consensus processing against the local delay; if processing happens first, it skips submission, otherwise it submits and waits for processing.

# Fix Pattern

Replace exclusive randomized submitter responsibility with deterministic staggered eventual responsibility: validators may delay submission to reduce duplicate load, but every validator retains an eventual local submission fallback.

## How It Was Fixed

The patch adds TransactionDigest::into_bytes to provide deterministic seed bytes, replaces boolean selected-submitter logic with position_submit_certificate, computes a stake-aware validator position from a digest-seeded shuffled committee order, and updates submit_and_wait so a validator submits after its delay unless consensus processing has already occurred. Tests were updated to check that all validators receive valid positions and at least one has zero delay.

# Why It Matters

1. Prevents malicious client delivery from indefinitely blocking validators that hold pending certificates.

2. Protects end-of-epoch checkpoint progress from a denial-of-service condition.

3. Preserves consensus load reduction through staggered rather than immediate universal submission.

4. Evidence supports liveness/availability impact, not consensus safety failure, forgery, privilege escalation, or fund loss.
