# Summary

The patch improves consensus adapter resilience by adding user-transaction backpressure before consensus submission, using a fixed 60 second certificate sequencing timeout, reducing listener queue capacity, adding inflight metrics, and improving capacity diagnostics. The evidence supports resource-control hardening, but does not prove an exploitable denial-of-service vulnerability, consensus safety issue, replay flaw, signature-validation flaw, or authorization bypass.

## Before/After Behavior

Before the patch, shared-object certificates that needed consensus proceeded without the shown in-flight user consensus transaction guard, the consensus listener was spawned with an explicit pending transaction capacity of 1,000,000, generated validator config used delay_step: Some(15_000), and ListenerCapacityExceeded carried no count. After the patch, handle_certificate rejects requests with resource_exhausted when consensus_adapter.num_inflight_transactions() exceeds MAX_PENDING_CONSENSUS_TRANSACTIONS, ValidatorService::new uses timeout_secs with a 60 second default, generated config sets timeout_secs: Some(60), ConsensusListener::spawn relies on new default capacity behavior, and ListenerCapacityExceeded includes the pending count.

# Root Cause

The grounded issue is that prior consensus adapter behavior had weaker resource-control and timeout resilience: a very large listener queue, no shown in-flight user consensus guard at this ingress point, and adaptive timeout behavior that the commit says could become too low and cause amplified traffic. The evidence does not support a root cause involving signature validation, replay protection, authorization, transaction ordering, or consensus correctness.

## Walkthrough

1. A validator receives a CertifiedTransaction in handle_certificate.

2. The shown context verifies the certificate and checks idempotency before deciding whether consensus sequencing is needed.

3. For shared-object transactions without existing shared locks, the request enters the consensus path.

4. After the patch, that path first checks consensus_adapter.num_inflight_transactions().

5. If the count exceeds MAX_PENDING_CONSENSUS_TRANSACTIONS, the request is rejected with tonic::Status::resource_exhausted.

6. Validator startup now derives the consensus adapter timeout from timeout_secs, defaulting to 60 seconds.

7. Generated validator config now sets timeout_secs: Some(60) instead of delay_step: Some(15_000).

8. The listener spawn call no longer passes the old explicit 1,000,000 pending transaction capacity, matching the commit description of a lower default capacity.

9. The error type now carries the observed pending transaction count for diagnostics.

# Fix Pattern

Add bounded resource controls and conservative timeout configuration around consensus-adapter ingress, with diagnostic improvements for capacity pressure.

## How It Was Fixed

The patch adds an in-flight user consensus transaction check in authority_server.rs and returns resource_exhausted above the configured limit. It changes consensus timeout configuration to use timeout_secs with a 60 second default, updates generated validator config accordingly, removes the explicit 1,000,000 listener capacity argument in favor of the new default behavior, and includes the pending count in ListenerCapacityExceeded.

# Why It Matters

1. Limits accumulation of user-submitted consensus work.

2. Reduces risk of retry amplification from overly short adaptive timeouts.

3. Improves diagnostics for listener capacity pressure.

4. Does not establish a concrete attacker-triggered vulnerability from the supplied evidence.

5. Does not support replay, signature-validation, authorization, ordering, or consensus-safety claims.
