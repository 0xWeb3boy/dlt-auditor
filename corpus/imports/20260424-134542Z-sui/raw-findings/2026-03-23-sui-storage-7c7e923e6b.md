# Summary

## Before/After Behavior

Before the patch, the deny-list v2 written-object loop always called `object.owner.get_address_owner_address()` when collecting `(coin_type, owner)` data. After the patch, it checks `protocol_config.use_coin_party_owner()` and uses `object.owner.get_owner_address()` when enabled, otherwise preserving the previous address-owner-only behavior. The protocol config adds the feature flag, exposes an accessor, and enables it for version 118.

# Root Cause

The changed path used address-owner-only extraction for written coin objects even though party-owned coins may require a different owner-resolution method. The provided evidence shows a mismatch in owner selection, but not the downstream impact of that mismatch.

## Walkthrough

1. During programmable transaction processing, written objects are inspected when `enable_coin_deny_list_v2()` is active.

2. For each written object, the code derives a possible coin type with `object.type_().and_then(|ty| ty.coin_type_maybe())`.

3. Before the patch, owner extraction was always `object.owner.get_address_owner_address()`.

4. The patch adds a `use_coin_party_owner` feature flag to protocol configuration.

5. The patched loop uses `object.owner.get_owner_address()` when that flag is active and falls back to the previous address-owner extraction otherwise.

6. Protocol version 118 enables `cfg.feature_flags.use_coin_party_owner = true`.

7. The supplied evidence does not show whether the previous behavior allowed a deny-list bypass, incorrect acceptance, or any other exploitable transaction outcome.

# Fix Pattern

Introduce a protocol-gated behavior change and use the party-owner-aware owner accessor only when the new protocol feature flag is enabled.

## How It Was Fixed

The patch adds `use_coin_party_owner` to `FeatureFlags`, adds `ProtocolConfig::use_coin_party_owner()`, enables the flag for protocol version 118, and changes the deny-list v2 written-object owner lookup to call `get_owner_address()` when the flag is active.

# Why It Matters

1. Deny-list processing is security-sensitive because it depends on associating coin objects with owners.

2. Party-owned coins appear to need owner resolution that differs from address-owner-only extraction.

3. The patch may prevent incorrect deny-list accounting for party-owned coins.

4. Exploitability is not proven by the provided evidence.
