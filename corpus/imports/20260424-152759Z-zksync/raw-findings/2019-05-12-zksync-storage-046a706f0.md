# Summary

The supported finding is availability hardening in `handle_get_block_by_id`. The patch replaces an `expect(...)` on the COMMIT operation lookup with an explicit `None` check that returns a JSON `not found` error. The input block id is derived from the HTTP request path, so the old code could panic when a requested block had no stored COMMIT operation. Other changes in the commit, including timestamp fields, chrono support, and transaction hash formatting, are not established as security fixes by the supplied evidence.

## Observed Patch Facts

1. In `src/server/src/api_server.rs`, the patch replaces `let stored_commit_operation = storage.load_stored_op_with_block_number(block_id_u32,...` with `// FIXME: no expects in API server db requests, because they might fail temporarily a...`.

2. In `src/server/src/api_server.rs`, the patch adds `committed_at: None,`.

3. In `src/server/src/eth_sender.rs`, the patch replaces `format!("0x{:?}", hash));` with `format!("{:?}", hash));`.

4. In `src/storage/Cargo.toml`, the patch replaces `diesel = { version = "1.4.2", features = ["postgres", "serde_json", "r2d2"] }` with `diesel = { version = "1.4.2", features = ["postgres", "serde_json", "r2d2", "chrono"] }`.

## Before/After Behavior

Before the patch, `handle_get_block_by_id` parsed a request path `block_id` and then called `storage.load_stored_op_with_block_number(block_id_u32, ActionType::COMMIT).expect(...)`. If no COMMIT operation was found, the handler would panic. After the patch, the handler checks whether the lookup returned `None` and returns `ApiError { error: "not found" }` before unwrapping the stored operation. The block list timestamp additions and transaction hash formatting change are adjacent API or representation changes, not proven vulnerability fixes.

# Root Cause

The API handler treated a storage lookup for request-selected block state as infallible. A block id that parsed successfully but had no stored COMMIT operation was not handled as normal absent state and instead reached a panic via `expect(...)`.

## Walkthrough

1. A request reaches `handle_get_block_by_id` with a `block_id` path parameter.

2. The handler validates that the parameter exists and parses it as `u32`.

3. Before the patch, the handler immediately required a COMMIT operation for that block with `expect(...)`.

4. If storage returned `None`, the request path reached a panic instead of an HTTP error response.

5. After the patch, the handler checks for `None` and returns a JSON `not found` error.

6. Only after the presence check does the handler unwrap the stored commit and continue building the block details response.

7. The same commit includes timestamp, chrono, and transaction hash formatting changes, but the evidence does not tie those changes to a security invariant.

# Fix Pattern

Replace panic-based assumptions at the API/storage boundary with explicit handling of absent state for request-derived identifiers.

## How It Was Fixed

The COMMIT lookup result is now stored as an optional value, checked with `is_none()`, and converted into a structured `not found` API response when absent. The code unwraps only after the guard. The patch also adjusts response fields and transaction hash formatting, but those are treated as secondary support or cleanup based on the provided evidence.

# Why It Matters

1. Request-derived block ids can refer to absent storage state.

2. A panic in an HTTP handler is an availability risk.

3. Returning a structured `not found` response avoids crashing the handler on missing COMMIT state.

4. The evidence does not show theft, forged blocks, invalid proofs, replay impact, or consensus failure.

# Evidence Notes

The strongest evidence is the change in `src/server/src/api_server.rs`: `storage.load_stored_op_with_block_number(...).expect(...)` became an optional lookup with an explicit `None` guard returning `ApiError { error: "not found" }`. The added comment says API server DB requests should avoid `expect` because failures may bring down the server.
