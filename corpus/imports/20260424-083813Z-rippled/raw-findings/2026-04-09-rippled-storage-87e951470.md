# Summary

The patch likely fixes an access-control issue in delegated granular transaction permissions. The evidence supports that delegated permission handling was centralized in `Transactor::checkPermission` and that transaction-specific granular semantics, especially for `TrustSet`, are now checked using derived held granular permissions. The evidence does not prove an exploit path, attacker preconditions, or concrete asset impact, so the verdict is downgraded from confirmed to likely.

## Observed Patch Facts

1. In `src/libxrpl/tx/transactors/account/AccountSet.cpp`, the patch replaces `NotTEC` with `TER`.

2. In `src/libxrpl/tx/Transactor.cpp`, the patch replaces `auto const delegateKey = keylet::delegate(tx[sfAccount], *delegate);` with `auto const sle = view.read(keylet::delegate(tx[sfAccount], *delegate));`.

3. In `src/libxrpl/tx/transactors/token/TrustSet.cpp`, the patch replaces `// if the trustline does not exist, granular permissions are` with `// granular permissions are not allowed to create a trustline`.

4. In `src/libxrpl/tx/transactors/token/TrustSet.cpp`, the patch replaces `TrustSet::checkPermission(ReadView const& view, STTx const& tx)` with `TrustSet::checkGranularSemantics(`.

## Before/After Behavior

Before the patch, `AccountSet` and `TrustSet` had transaction-specific delegated permission handling that read `sfDelegate` and delegate ledger entries locally. After the patch, the central `Transactor::checkPermission` path reads the delegate entry, rejects missing delegate permissions, accepts full transaction permission, checks whether the transaction type supports granular permissions, and derives held granular permissions for transaction-specific semantic checks. `TrustSet` now receives held granular permissions and applies operation-level restrictions such as rejecting granular trustline creation and requiring explicit granular permissions for supported trustline actions.

# Root Cause

Delegated granular authorization was split between the central transaction path and transaction-specific handlers, creating risk of inconsistent interpretation of granular permissions. The provided evidence supports an authorization-consistency issue, but not the exact pre-patch bypass condition.

## Walkthrough

1. A transaction with `sfDelegate` enters delegated permission handling.

2. The patched central path reads the delegate ledger entry with `keylet::delegate(tx[sfAccount], *delegate)`.

3. If the delegate entry is missing, the transaction is rejected with `terNO_DELEGATE_PERMISSION`.

4. If `checkTxPermission(sle, tx)` succeeds, full transaction permission is accepted.

5. If full transaction permission is absent, the patched path checks whether the transaction type supports granular permissions.

6. Granular permissions are derived centrally and passed to transaction-specific semantic checks.

7. `TrustSet::checkGranularSemantics` rejects granular delegated trustline creation when the trustline does not already exist.

8. `TrustSet` constrains freeze, unfreeze, and authorization operations to explicitly held granular permissions.

9. The shown `AccountSet` local permission block was removed, suggesting reliance on the shared permission path.

# Fix Pattern

Centralize delegate entry lookup and transaction-level permission checks, then pass derived granular permissions into transaction-specific semantic validation.

## How It Was Fixed

`Transactor::checkPermission` was updated to own the shared delegated permission flow. Transaction-specific code such as `TrustSet` now validates operation semantics against held granular permissions instead of independently loading and interpreting delegate permissions. The shown `AccountSet` local delegated permission function was removed.

# Why It Matters

1. Granular delegation is security-sensitive because it grants limited authority to another account.

2. Permission checks must distinguish full transaction permission from narrower operation permission.

3. Inconsistent per-transaction checks can over-authorize delegated actions.

4. The provided evidence does not establish unauthorized fund movement, consensus failure, memory corruption, or denial of service.
