# Summary

The patch adds a missing runtime check in the fault-proof proposer so it skips game creation when the proposer's configured `game_type` does not match the registry's current respected game type. That is a real behavior change in a critical path, but the provided evidence does not establish an exploitable vulnerability, attacker control, or harmful onchain acceptance of mismatched games, so this is best treated as unclear security relevance rather than a confirmed security fix.

## Before/After Behavior

Before the patch, the shown proposer path proceeded into later game-creation logic without any visible check against the live respected game type. After the patch, the proposer queries `AnchorStateRegistry.respectedGameType()`, compares it to `self.config.game_type`, logs a warning on mismatch, and returns early to skip creating a game.

# Root Cause

The proposer creation path relied on locally configured game type without consulting the live onchain policy source that defines the currently respected type. The surrounding config and ABI plumbing also did not yet expose the registry query needed to enforce that check in this path.

## Walkthrough

1. `fault-proof/src/proposer.rs` adds a new precondition before continuing with game creation.

2. The new code calls `self.anchor_state_registry.respectedGameType().call().await?` to fetch the live respected type.

3. If `self.config.game_type` differs from that value, the proposer logs a warning and returns `Ok((false, U256::ZERO, u32::MAX))`, skipping creation.

4. `fault-proof/src/contract.rs` adds the `respectedGameType()` ABI entry needed for that query.

5. `fault-proof/src/config.rs` adds `ANCHOR_STATE_REGISTRY_ADDRESS` so the proposer can be configured with the registry address.

6. `fault-proof/bin/proposer.rs` constructs an `AnchorStateRegistry` client from config and the L1 provider, enabling the runtime check.

# Fix Pattern

Add an explicit live-policy validation immediately before a sensitive action, and wire the policy source through config and ABI layers so the component can fail closed when local configuration diverges from current protocol policy.

## How It Was Fixed

The fix introduces a guard in the proposer's game-creation flow that reads the respected game type from `AnchorStateRegistry` and exits early on mismatch. Supporting changes add the ABI method, load the registry address from configuration, and initialize the registry client during proposer startup.

# Why It Matters

1. It prevents this proposer component from creating games when its local configuration no longer matches the protocol's current respected type.

2. It reduces mistakes caused by stale or incorrect operator configuration.

3. It hardens a critical workflow, but the supplied evidence does not show broader protocol impact beyond this component's behavior.
