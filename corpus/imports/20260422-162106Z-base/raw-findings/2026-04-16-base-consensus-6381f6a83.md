## Before/After Behavior

Before the patch, a successful TEE proof was stored as a plain TEE pending entry, and a submission failure was treated as a retry case without stored ZK fallback metadata. The retry path for `ProofKind::Tee` could drop the entry because there was no ZK request attached. After the patch, the pending TEE state can carry optional pre-built ZK fallback request and intent, TEE submission failure is redirected into fallback handling, and the retry path can transition that work item into ZK proving instead of only retrying or dropping it.

# Root Cause

The pending-proof and retry logic for TEE proofs did not preserve or use the information needed to transition from a failed TEE submission into the alternate ZK path. This is a state-management and retry-flow defect, not evidence of a cryptographic or consensus flaw.

## Walkthrough

1. `initiate_proof()` still tries the TEE-first path when eligible and a TEE proof is obtained.

2. Before the fix, the code stored a ready TEE proof without attached ZK fallback request or fallback intent.

3. The old retry logic treated bare `ProofKind::Tee` as having no ZK session to restart and could remove the pending entry.

4. The patch changes TEE pending state so it may carry `zk_fallback_request` and `zk_fallback_intent`.

5. On TEE dispute transaction failure, the driver now marks the item for retry and routes into fallback handling with a log message stating it is falling back to ZK.

6. `handle_proof_retry()` now has a TEE branch that uses the stored fallback request and intent when present; if fallback construction previously failed, the fields can be `None` and the entry may still be dropped later.

# Fix Pattern

Preserve alternate-path state at creation time and make retry handling perform an explicit state transition to that fallback path instead of retrying the original path indefinitely or discarding the work item.

## How It Was Fixed

The patch stores optional ZK fallback request and intent alongside pending TEE proofs, detects TEE-specific submission failures, and reuses the retry path to switch the pending work into the ZK branch. The commit message also says the retry budget is reset on TEE-to-ZK transition and that fallback-build failure is handled explicitly by leaving fallback fields absent rather than discarding the TEE proof immediately.

# Why It Matters

1. Reduces a challenger liveness failure that otherwise required manual operator action.

2. Makes the retry path preserve intended fallback behavior instead of losing it for TEE proofs.

3. Improves robustness of dispute processing, but the supplied evidence does not prove a security exploit.
