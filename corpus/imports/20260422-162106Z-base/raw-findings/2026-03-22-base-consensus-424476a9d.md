# Summary

This patch appears to harden a consensus-sensitive sequencer start path. The provided code shows that `start_sequencer` previously logged the supplied `unsafe_head` and activated the sequencer without validating engine state; after the change it fetches the engine unsafe head and rejects zero/uninitialized state. The commit text also says it now rejects caller/engine head mismatches, but that exact comparison is not present in the supplied excerpt, so that part is supported by commit metadata rather than the shown hunk.

## Before/After Behavior

Before the patch, the sequencer start path in `crates/consensus/service/src/actors/sequencer/admin_api_impl.rs` logged `unsafe_head` and set `self.is_active = true` after earlier checks, with no shown validation of the engine's current unsafe head. The devnet caller in `devnet/src/l2/in_process_consensus.rs` also passed `B256::ZERO` because the server was described as only logging the value. After the patch, `start_sequencer` queries the engine for its unsafe head, turns fetch failures into request errors, and rejects a zero/uninitialized engine head; the commit body further states that a caller-provided head mismatch is rejected. Supporting changes initialize and publish engine state earlier so callers can obtain a non-zero unsafe head before requesting sequencer start.

# Root Cause

The start path accepted activation without enforcing that the execution engine had a valid current unsafe head, and the supplied `unsafe_head` was not shown to influence the transition before activation. Separate state-publication timing also meant callers could continue observing a zero unsafe head until later engine activity, making invalid start requests more likely.

# Fix Pattern

Validate engine state at the activation boundary, fail closed on uninitialized or inconsistent state, and publish the authoritative state early enough that callers can satisfy the new preconditions.

## How It Was Fixed

The patch changed sequencer start from a log-only transition to a validated one. It now fetches the engine's current unsafe head, rejects start when that head is still zero/uninitialized, and according to the commit body also rejects mismatched caller-provided heads. The surrounding engine and devnet changes make the current unsafe head observable and pass the real value instead of a placeholder.

# Why It Matters

1. It reduces the chance of activating sequencing before the engine has established a usable L2 tip.

2. It reduces the chance of starting sequencing from a tip that differs from the engine's current view.

3. It strengthens a consensus-critical state transition even though the provided evidence does not show a remote exploit or production incident.

4. It ties caller behavior and engine state to the same start-time invariant instead of relying on a logged but ignored parameter.
