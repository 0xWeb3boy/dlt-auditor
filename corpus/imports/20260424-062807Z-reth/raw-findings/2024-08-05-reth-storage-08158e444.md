# Summary

The patch adds an explicit parent-header validation step to the engine2 block insertion path. The evidence supports that this path previously validated the block and checked parent state availability, but did not perform a visible parent-relative header check here. After the change, it fetches the parent sealed header, fails if that header is missing, and rejects the block if `validate_header_against_parent` fails. The test utility timestamp change is supporting evidence that parent-relative header rules are now enforced.

## Before/After Behavior

Before the patch, `insert_block_inner` called `self.validate_block(&block)?` and checked for parent state, but the provided diff does not show a parent-header lookup or a parent-relative header validation step in this path. After the patch, the code retrieves the parent sealed header with `self.sealed_header_by_hash(block.parent_hash)?`, turns absence into `ProviderError::HeaderNotFound`, and calls `self.consensus.validate_header_against_parent(&block, &parent_block)`, aborting on error.

# Root Cause

This insertion path was missing an explicit check that the incoming header was valid relative to its declared parent. The code path relied on block validation and parent state availability without a visible parent-header validation gate at this point.

## Walkthrough

1. `insert_block_inner` handles insertion of a new `SealedBlockWithSenders` into the engine tree path.

2. The pre-patch flow already checked for duplicate blocks, called `self.validate_block(&block)?`, and required parent state availability before continuing.

3. The provided old-path evidence does not show a parent-header fetch or a call that validates the child header against its parent in this function.

4. The patch adds `sealed_header_by_hash`, which returns a `SealedHeader` rather than a full block, matching the new need to validate against the parent header.

5. The insertion path now fetches `block.parent_hash` as a sealed header and converts a missing parent header into `ProviderError::HeaderNotFound`.

6. With that parent header in hand, the new code calls `self.consensus.validate_header_against_parent(&block, &parent_block)` and returns an error immediately if validation fails.

7. The test helper now sets `timestamp: number` with a note about monotonic increase, which supports that ancestry-dependent header validation is now exercised by tests.

# Fix Pattern

Fetch the referenced parent header inside the import path and enforce a fail-closed parent-relative consensus check before further processing continues.

## How It Was Fixed

The implementation introduces `sealed_header_by_hash` so the engine can retrieve a parent `SealedHeader` from in-memory state or backing storage, then uses that header in `insert_block_inner` to call `validate_header_against_parent`. Missing parents are surfaced as `HeaderNotFound`, and validation failures now stop insertion immediately. A test helper was updated so generated blocks satisfy the stricter parent-relative timestamp requirement.

# Why It Matters

1. This is a consensus-sensitive acceptance path for new blocks.

2. Without a parent-relative header check here, the path could advance blocks that were not yet shown valid against their declared parent.

3. The new behavior fails closed when the parent header is unavailable or the child-parent relationship is invalid.

4. The test change suggests at least one enforced rule is monotonic parent/child timestamp behavior.

5. The evidence supports a real validation gap in this path, but not a broader exploit narrative beyond that.
