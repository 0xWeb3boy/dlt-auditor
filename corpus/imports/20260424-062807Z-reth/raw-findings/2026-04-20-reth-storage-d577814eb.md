## Before/After Behavior

Before the change, `validate_block_access_list_presence` grouped `V5` with `V1`-`V4`, and related errors described block access list and slot-number support as a coarse pre-`V6` condition. After the change, `V5` has its own branch, payload-specific Amsterdam checks are added there, and the errors now describe support in terms of the current engine API version instead of a simple `before V6` threshold.

# Root Cause

The visible root cause is overly coarse validation logic: Amsterdam-specific field handling was modeled with a broad version cutoff and grouped `V5` with older versions, instead of validating against the exact engine method version, message kind, and Amsterdam activation state.

## Walkthrough

1. `crates/payload/primitives/src/lib.rs` changes `validate_block_access_list_presence` so `EngineApiMessageVersion::V5` is no longer handled together with `V1`-`V4`.

2. The new `V5` branch adds `MessageValidationKind::Payload` logic tied to `is_amsterdam_active` and `has_block_access_list`, showing a more specific fork/version check.

3. `crates/payload/primitives/src/error.rs` replaces `BlockAccessListNotSupportedBeforeV6` with `BlockAccessListNotSupported`, changing the rule from a blanket cutoff to method-version-specific support.

4. The same error-shape change is made for slot numbers, which supports the interpretation that this is endpoint-validation alignment rather than a one-off bugfix.

5. Documentation in `crates/payload/primitives/src/lib.rs` was updated to describe Amsterdam as `V6` territory and to say staggered endpoint upgrades should reject the next fork once a newer method version is required.

# Fix Pattern

Replace coarse version-threshold validation with explicit per-endpoint branching and fork-aware checks, then align error reporting with the exact method-version rules.

## How It Was Fixed

The patch separates `V5` handling from the older versions in block-access-list validation, adds Amsterdam-aware checks for payload messages in that branch, and renames validation errors so they describe unsupported fields in the current engine API version rather than implying a universal pre-`V6` prohibition. The accompanying docs were updated to match that stricter endpoint/fork model.

# Why It Matters

1. Consensus-facing API validation should match exact fork and endpoint rules, not approximate them with broad version buckets.

2. A coarse cutoff can reject or accept Amsterdam-era fields under the wrong method version during staggered upgrades.

3. The evidence shows a protocol-correctness fix, but not that invalid payloads reached chain state or that a security failure occurred.
