## Before/After Behavior

Before the patch, `all_chain_hashes` walked parent chains and extended a `BTreeMap<BlockNumber, BlockHash>` with every visited chain's blocks, which could mix overlapping parent heights into the result. After the patch, the code explicitly handles overlapping parent numbers, derives a height bound from the current branch view or chain tip, filters out blocks above that bound, and uses guarded insertion so an existing hash for a block number is preserved.

# Root Cause

The function rebuilt a sidechain's number-to-hash map by repeatedly merging ancestor chains into a single map keyed only by block number. That aggregation did not adequately constrain overlapping parent heights or inherited blocks above the original branch tip.

## Walkthrough

1. The changed function `all_chain_hashes` returns block hashes for a sidechain and previously accumulated them with `hashes.extend(...)` while walking parent chains.

2. Because the accumulator is a `BTreeMap<BlockNumber, BlockHash>`, repeated merges could overwrite or otherwise conflate entries when different traversed chains used the same block number.

3. The new comments identify the specific edge case: parent chains may contain overlapping block numbers or numbers greater than the original chain tip.

4. The patch computes `latest_block_number` from the accumulated map or the current chain tip and filters traversed blocks with `b.number <= latest_block_number`.

5. The added `btree_map::Entry` import and comment indicate the revised logic keeps an existing mapping for a block number instead of blindly replacing it.

6. A new `sidechain_block_hashes` test was added in `blockchain_tree.rs`, and the storage test helper was adjusted to provide revert data needed for that scenario.

# Fix Pattern

Replace unconditional ancestry-map merging with bounded, first-entry-preserving reconstruction for branch-local state.

## How It Was Fixed

The fix changes `all_chain_hashes` from a blind `BTreeMap::extend` over each traversed chain into logic that explicitly accounts for overlapping parent block numbers and caps inherited entries at the original branch tip. The accompanying test additions exercise sidechain hash behavior, while the storage helper change appears to support that regression setup.

# Why It Matters

1. Prevents sidechain hash reconstruction from mixing in parent-chain entries at the same height.

2. Keeps the reconstructed branch view bounded to the original sidechain tip.

3. Improves correctness of fork/sidechain bookkeeping in blockchain-tree.

4. The supplied evidence does not show attacker-triggered exploitation or a demonstrated consensus split.
