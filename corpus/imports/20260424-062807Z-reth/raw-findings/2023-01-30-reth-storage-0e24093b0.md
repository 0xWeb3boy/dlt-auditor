## Before/After Behavior

Before the patch, the shown `AccountInfoChangeSet::Created` path unconditionally inserted created accounts, and the shown execution-stage loop did not yet expose a per-block Spurious Dragon activation check at that point. The shown `Account` impl also lacked the shared `is_empty()` predicate in the extracted snippet. After the patch, `Account::is_empty()` defines post-Spurious-Dragon emptiness, execution-stage insertion derives fork activation from block number, and created empty accounts are skipped when state clearing is active. The unwind path also changes from direct put/delete behavior to cursor-based delete plus conditional restore, which looks like consistency support rather than the main root cause from the supplied evidence.

# Root Cause

The account persistence path did not consistently encode and apply the fork-aware empty-account rule. As shown by the added `is_empty()` helper and the new guard in `AccountInfoChangeSet::Created`, empty accounts could be inserted even when post-Spurious-Dragon state clearing should suppress them. The storage-unwind change may help keep rollback exact, but the supplied excerpts do not prove it was the root cause of the vulnerability.

## Walkthrough

# Fix Pattern

Centralize the protocol predicate, thread fork-activation context into the mutation path, reject writes that violate the fork rule, and tighten rollback logic so restored state matches the intended prior view.

## How It Was Fixed

The fix introduces a canonical `Account::is_empty()` helper, computes when Spurious Dragon becomes active for each processed block, and uses that fork-aware flag to skip persisting newly created empty accounts when state clearing is in effect. The unwind code is also made more exact by deleting any current plain-storage entry before conditionally restoring the prior non-zero value.

# Why It Matters

1. Fork-specific state rules must be applied exactly where state is written, not inferred later.

2. Persisting accounts that should be treated as empty can leave plain state inconsistent with protocol rules.

3. In a blockchain client, protocol-inconsistent execution state is security-relevant even without a demonstrated exploit chain in the provided excerpts.

4. The supplied evidence supports the account-handling issue directly; claims of broader impact should stay bounded.
