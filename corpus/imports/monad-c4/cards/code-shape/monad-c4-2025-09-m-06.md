## Code Shape Summary

- Short description of what the buggy code looked like: The callback stored one coordinate in the timer event and another inside the pending vote. When the timer fired late, it dequeued the newer vote but routed it using the older timer round.

## Search Motifs

- handle_vote_timer(round) reads VoteReady(v) but calls send helper with round instead of v.round
- leader selection derives from callback parameter rather than object coordinate
- timer for R+1 can fire after scheduled vote changed to R+2 or later
- rescheduled timer coordinate follows stale callback round

## Typical Asymmetry

- What was checked in one path but missing in another: handle_vote_timer(round) reads VoteReady(v) but calls send helper with round instead of v.round

## Patch Pattern

- What the fix changed structurally: Derive vote recipients and rescheduled timer coordinates from the stored vote round, and treat mismatched timer rounds as stale telemetry or no-op conditions.

## False Match Warnings

- No issue if the send helper only accepts the vote object and derives all routing from v.round
- No issue if stale timer callbacks are ignored or checked against the stored vote coordinate before side effects
- Impact is lower if duplicate vote routing to both current and next leaders is robust to coordinate drift
