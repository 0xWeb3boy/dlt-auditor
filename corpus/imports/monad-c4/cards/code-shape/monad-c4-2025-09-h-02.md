## Code Shape Summary

- Short description of what the buggy code looked like: The same EIP-7702 authorization predicates existed in txpool and block validation, but their order changed the validity outcome. Txpool treated a wrong-chain authorization as skipped before seeing the forbidden system authority, while block validation saw the system authority first and rejected the whole block.

## Search Motifs

- EIP-7702 authorization chain-id skip runs before special system-sender check in one layer
- another layer checks system or privileged authority before chain-id skip
- invalid child authorization is ignored in txpool but fatal in block validation
- failed predicate order changes whether child, transaction, or block is rejected

## Typical Asymmetry

- What was checked in one path but missing in another: EIP-7702 authorization chain-id skip runs before special system-sender check in one layer

## Patch Pattern

- What the fix changed structurally: Make EIP-7702 authorization validation order and failure disposition identical across txpool, block validation, block policy, and execution. In particular, reject or drop system-sender authorizations before chain-id skip logic if that is the block-validation rule.

## False Match Warnings

- No issue if all layers return the same parent-transaction validity result for every failing predicate
- No issue if txpool rejects the transaction before proposal or block validation only rejects the authorization side effect
- Impact is lower if invalid proposals are not retried and the offending transaction is evicted from hot pools
