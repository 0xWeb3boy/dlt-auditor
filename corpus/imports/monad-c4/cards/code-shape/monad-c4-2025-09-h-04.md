## Code Shape Summary

- Short description of what the buggy code looked like: Txpool and block policy derived delegated status at different times. Txpool treated a sender as non-delegated until the authorization transaction appeared in order, while block policy collected all authorizations up front and applied delegated status to the entire block.

## Search Motifs

- block-level prepass collects all EIP-7702 authorities before ordered transaction validation
- txpool mutates is_delegated only after including the authorization transaction
- reserve or emptying classification of an earlier transaction depends on a later transaction
- tests lack two-transaction ordering witnesses for delegated status

## Typical Asymmetry

- What was checked in one path but missing in another: block-level prepass collects all EIP-7702 authorities before ordered transaction validation

## Patch Pattern

- What the fix changed structurally: Carry order information into block-policy accounting, such as whether delegation existed before the first transaction, or validate EIP-7702 delegated status using the same ordered transition model as proposal assembly.

## False Match Warnings

- No issue if block policy records whether delegation existed before the first transaction and applies ordered semantics
- No issue if txpool and block policy share the same whole-block prepass and reserve rules
- Impact is lower if rejected proposals evict the pair or if the account balance cannot be tuned across the emptying/non-emptying boundary
