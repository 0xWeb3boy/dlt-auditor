## Code Shape Summary

- Short description of what the buggy code looked like: Txpool insertion used a cheaper base-fee-only balance check, while proposal/block policy used the full gas bid. Attackers could fill tracked pools with transactions that looked affordable at insert time but could never pass proposal validation.

## Search Motifs

- txpool admission checks balance against base_fee * gas_limit only
- proposal or block policy uses compute_txn_max_gas_cost including priority fee
- forwarding checks max_fee >= base_fee but not sender affordability at full bid
- proposal failure leaves transaction tracked, hot, or repeatedly selected

## Typical Asymmetry

- What was checked in one path but missing in another: txpool admission checks balance against base_fee * gas_limit only

## Patch Pattern

- What the fix changed structurally: Tighten txpool insertion and forwarding to use the full type-aware max-gas-cost helper, and evict or demote transactions that fail static affordability during proposal building.

## False Match Warnings

- No issue if txpool insertion and forwarding use the same full-bid max-cost helper as proposal validation
- No issue if a later affordability failure evicts or demotes the transaction so it cannot starve proposals
- Impact is lower when pool capacity, per-sender limits, or rate limits prevent broad stuffing
