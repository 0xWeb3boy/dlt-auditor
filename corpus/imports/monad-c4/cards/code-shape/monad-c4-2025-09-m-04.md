## Code Shape Summary

- Short description of what the buggy code looked like: The trim helper read a partial page at the original boundary, advanced the range to skip that page for discard, then wrote the preserved buffer using the advanced range offset. The preserved data could overwrite the next page.

## Search Motifs

- partial-page trim preservation reads from one offset and writes after mutating the offset variable
- range[0] or cursor is advanced before pwrite of preserved bytes
- discard/trim/punch-hole helper reuses a mutable range array for both preservation and discard
- block-device trim tests do not cover unaligned truncation boundaries

## Typical Asymmetry

- What was checked in one path but missing in another: partial-page trim preservation reads from one offset and writes after mutating the offset variable

## Patch Pattern

- What the fix changed structurally: Write the partial page back before advancing the discard range, or save the original page offset in a separate variable and use it for pwrite; add unaligned trim regression tests.

## False Match Warnings

- No issue if the preserved page is written before the discard range offset is advanced
- No issue if the original offset is stored separately and used for pwrite
- Impact is lower if only regular files use the code path and block devices are not supported in production
