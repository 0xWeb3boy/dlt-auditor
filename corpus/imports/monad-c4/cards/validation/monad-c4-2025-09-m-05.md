## What Confirmed The Issue

- Evidence 1: The report shows debug_getRawReceipts calling r.encode(&mut res) for ReceiptEnvelope.
- Evidence 2: The same file already used encode_2718 for raw transactions, highlighting the asymmetric encoding shape.
- Evidence 3: Current upstream raw receipt encoding calls r.encode_2718(&mut res).

## What Could Have Invalidated It

- Compensating control 1: The receipt type encode method already includes the envelope byte in this dependency version.
- Compensating control 2: The API is intentionally payload-only and clearly not advertised as EIP-2718 raw receipt bytes.

## Severity Guidance

- Expected impact band: standard-nonconformance
- Expected severity band: medium

## False-Positive Cautions

- Caution 1: No issue if the API explicitly returns inner receipt payloads and clients are documented to expect that nonstandard format
- Caution 2: No issue if ReceiptEnvelope::encode already includes the typed envelope in the library version used
- Caution 3: Impact is lower if the API is disabled, admin-only, or not used by external tooling
