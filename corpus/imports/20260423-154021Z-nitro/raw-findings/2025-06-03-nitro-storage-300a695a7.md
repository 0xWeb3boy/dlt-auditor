## Before/After Behavior

Before the patch, initial state recovery used only the parent-chain block hash and could stop rebuilding delayed-message tracking as soon as seen/read counters matched. After the patch, startup fetches the finalized parent-chain block, passes its number into initial-state recovery, and only treats delayed-message metadata as safely discardable when the relevant parent-chain position is finalized.

# Root Cause

Recovery logic relied on local read-progress (`DelayedMessagedSeen == DelayedMessagesRead`) without also checking whether the underlying parent-chain position was finalized, so restart-time reconstruction could drop or omit tracking data for still-reorgable history.

## Walkthrough

1. `mel.go` now reads the finalized parent-chain block before loading initial MEL state.

2. The startup path switches from `GetState(...)` to `FetchInitialState(..., finalizedBlk.NumberU64())`, adding finalization context to recovery.

3. `database.go` replaces `initializeSeenDelayedMsgInfoQueue` with `initializeSeenUnreadDelayedMetaDeque(ctx, state, finalizedBlock)`.

4. The new initializer only returns early when delayed messages are fully read and the state's parent-chain block number is at or before the finalized block.

5. When the current state is ahead of finality, the code may load `d.State(ctx, finalizedBlock)` to rebuild delayed-message metadata from finalized history.

6. `types/state.go` updates accessors and trimming semantics so delayed-message metadata is retained until the corresponding parent-chain position is finalized.

# Fix Pattern

Thread an explicit finalized-boundary parameter through recovery code, and gate state initialization and trimming on finality rather than read-progress alone.

## How It Was Fixed

The patch fetches the finalized parent-chain block during MEL startup, passes that block number into database recovery, and changes delayed-message deque initialization/trimming so metadata from unfinalized history is retained or reconstructed instead of being dropped solely because it was already marked read.

# Why It Matters

1. Improves restart behavior across parent-chain reorgs.

2. Prevents delayed-message tracking from depending only on local read counters.

3. Shows integrity hardening in a consensus-adjacent path, but not a proven exploitable flaw.
