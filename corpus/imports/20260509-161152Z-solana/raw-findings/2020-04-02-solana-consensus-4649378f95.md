# Summary

The patch changes Solana ReplayStage fork vote selection so `tower.check_switch_threshold(...)` is evaluated for the heaviest candidate bank and `switch_threshold` is required in the final vote condition. This is consensus-sensitive and may be security relevant, but the supplied evidence does not establish a concrete vulnerability, exploit path, or confirmed safety impact.

## Observed Patch Facts

1. In `core/src/replay_stage.rs`, the patch replaces `let selected_same_fork = ancestors` with `let switch_threshold = tower.check_switch_threshold(`.

2. In `core/src/replay_stage.rs`, the patch replaces `let voted_on_different_fork = {` with `Self::log_leader_change(`.

3. In `core/src/replay_stage.rs`, the patch replaces `// If we voted on a different fork, update the earliest vote` with `let start = allocated.get();`.

4. In `core/src/replay_stage.rs`, the patch replaces `if !is_locked_out && vote_threshold && propagation_confirmed {` with `if !switch_threshold {`.

## Before/After Behavior

Before the patch, the code could classify the heaviest bank as being on the same fork using `earliest_vote_on_fork`, select `votable_bank_on_same_fork` without the shown switch-threshold call on that path, and later vote when `!is_locked_out && vote_threshold && propagation_confirmed` without also requiring `switch_threshold`. It also tracked `voted_on_different_fork` and updated `earliest_vote_on_fork` plus cleared `switch_threshold` after such votes. After the patch, ReplayStage computes `switch_threshold` with `tower.check_switch_threshold(...)`, records `FailedSwitchThreshold` when false, and only votes when `switch_threshold` is also true. The separate `voted_on_different_fork` bookkeeping and post-vote reset logic are removed.

# Root Cause

The old ReplayStage logic kept switch-threshold state partly in side bookkeeping and did not include `switch_threshold` in the final vote-producing condition. The evidence supports a vote-gating logic bug, but not a proven exploitable security vulnerability.

## Walkthrough

1. ReplayStage evaluates a heaviest candidate bank while choosing a fork to vote on.

2. The old code checked whether the candidate appeared on the same fork using `earliest_vote_on_fork`.

3. When that same-fork path was taken, the shown code selected `votable_bank_on_same_fork` rather than using the new `tower.check_switch_threshold(...)` flow.

4. The old final vote condition required lockout, vote threshold, and propagation confirmation, but not `switch_threshold`.

5. The old vote loop also tracked `voted_on_different_fork` and performed post-vote updates to `earliest_vote_on_fork` and `switch_threshold`.

6. The new code computes `switch_threshold` for the heaviest candidate bank.

7. The new code adds `FailedSwitchThreshold` to failure reasons when that predicate fails.

8. The new final vote condition requires `switch_threshold` before voting.

# Fix Pattern

Make the consensus predicate an explicit gate at the vote decision point instead of relying on fork-classification shortcuts and post-vote bookkeeping.

## How It Was Fixed

The patch removes the same-fork shortcut around switch-threshold evaluation, removes `voted_on_different_fork` and related post-vote state updates, adds failure reporting for failed switch threshold, and includes `switch_threshold` in the final condition that permits voting.
