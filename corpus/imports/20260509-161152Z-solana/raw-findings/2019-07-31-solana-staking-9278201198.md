## Before/After Behavior

Before the patch, the provided withdrawal hunk entered `StakeState::Stake(mut stake)` and computed `staked` using `stake.stake(clock.epoch)` without the shown explicit rejection for still-activated stake. After the patch, withdrawal first fails with `InstructionError::InsufficientFunds` if the stake is still activated, then computes staked balance using `stake.stake(clock.stakers_epoch)`. The runtime test changes check `epoch_vote_accounts(epoch)` and expected leader stake for that epoch.

# Root Cause

The withdrawal path did not directly enforce the still-activated stake lock in the provided before hunk and used `clock.epoch` rather than `clock.stakers_epoch` for the staked-balance calculation. The evidence supports an epoch/accounting mismatch and missing withdrawal guard, but does not prove a concrete external exploit path.

# Fix Pattern

Add an explicit state guard before withdrawal and align stake-balance evaluation with the stakers epoch used by epoch stake accounting.

## How It Was Fixed

The withdrawal path now returns `InstructionError::InsufficientFunds` for still-activated stake and uses `clock.stakers_epoch` when calculating the staked amount. Tests were adjusted to assert epoch-specific vote-account stake behavior.

# Why It Matters

1. Activated delegated stake should not be withdrawable before deactivation.

2. Withdrawal checks should use the same epoch basis as stake/vote accounting.

3. The evidence supports stake-lock and accounting correctness, not a demonstrated theft or consensus-fork scenario.
