# Summary

The patch is likely an access-control fix in Solana's vote API. The strongest supported change is that withdrawals now verify `vote_state.authorized_withdrawer` using a shared authorized-signer path, instead of only requiring the vote account itself to sign. Vote processing was also moved from inline authorized-voter signer matching to a shared helper, and the authorization API was generalized to handle voter or withdrawer roles.

## Observed Patch Facts

1. In `programs/vote_api/src/vote_state.rs`, the patch replaces `if vote_account.signer_key().is_none() {` with `other_signers: &[KeyedAccount],`.

2. In `programs/vote_api/src/vote_state.rs`, the patch replaces `if vote_state.authorized_voter_pubkey == Pubkey::default() {` with `if vote_state.authorized_voter == Pubkey::default() {`.

3. In `programs/vote_api/src/vote_state.rs`, the patch replaces `/// Authorize the given pubkey to sign votes. This may be called multiple times,` with `/// Authorize the given pubkey to withdraw or sign votes. This may be called multiple...`.

4. In `programs/vote_api/src/vote_instruction.rs`, the patch replaces `process_instruction(&authorize_voter(` with `process_instruction(&authorize(`.

## Before/After Behavior

Before the patch, `withdraw` only checked whether `vote_account.signer_key()` existed. After the patch, `withdraw` accepts `other_signers`, loads `VoteState`, and verifies `vote_state.authorized_withdrawer`. Before the patch, vote processing manually checked signer presence against the stored authorized voter key. After the patch, it delegates that check to `verify_authorized_signer(&vote_state.authorized_voter, vote_account, other_signers)`. The authorization API changed from `authorize_voter` to a role-aware `authorize` taking `VoteAuthorize`.

# Root Cause

The withdrawal path used a generic vote-account signer requirement instead of checking the role-specific withdraw authority stored in vote account state. Related voter authorization logic was duplicated inline rather than routed through the shared authorized-signer verification helper.

## Walkthrough

1. `withdraw` previously rejected only when the vote account had no signer.

2. The patched `withdraw` loads `VoteState` and requires `verify_authorized_signer` for `vote_state.authorized_withdrawer`.

3. `process_vote` now verifies `vote_state.authorized_voter` through the same helper instead of maintaining local signer-search logic.

4. The authorization API was generalized from voter-only authorization to a `VoteAuthorize` role selector.

5. Instruction tests were updated to call the new `authorize` API and cover related invalid-account paths.

# Fix Pattern

Replace generic or duplicated signer checks with centralized, role-aware authorization checks against authority fields stored in account state.

## How It Was Fixed

The patch added `other_signers` to the withdrawal path, checked the stored authorized withdrawer before proceeding, reused shared authorized-signer verification for vote processing, and generalized authorization updates through a role parameter.

# Why It Matters

1. Withdrawals are gated by the authorized withdrawer role rather than a generic vote-account signature.

2. Vote signing and withdrawal authorization now follow a consistent role-check pattern.

3. The evidence supports an access-control fix, but not a proven exploit, theft scenario, or consensus failure.
