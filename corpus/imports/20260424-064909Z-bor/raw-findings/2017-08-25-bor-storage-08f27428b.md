# Summary

The patch adds an explicit destination-occupancy check to `EVM.Create` and returns `ErrContractAddressCollision` when the derived contract address is already in use. That is security-relevant protocol validation logic, but the provided evidence supports this more as implementation of Metropolis EIP-684 than as a demonstrated vulnerability fix for previously incorrect behavior in the applicable ruleset.

## Observed Patch Facts

1. In `core/vm/evm.go`, the patch replaces `// Create a new account on the state` with `// Ensure there's no existing contract already at the designated address`.

2. In `core/vm/errors.go`, the patch replaces `ErrOutOfGas = errors.New("out of gas")` with `ErrOutOfGas = errors.New("out of gas")`.

3. In `core/vm/evm.go`, the patch adds `// emptyCodeHash is used by create to ensure deployment is disallowed to already`.

## Before/After Behavior

Before the patch, the shown `Create` flow performed depth and balance checks, incremented the caller nonce, and then continued toward snapshot/account creation without any visible check that the derived contract address was unused. After the patch, it derives `contractAddr` earlier, reads the target nonce and code hash, and aborts with `ErrContractAddressCollision` if the address is already occupied; otherwise it proceeds into the creation flow.

# Root Cause

The shown pre-patch `Create` path lacked a destination-address occupancy check before continuing with contract creation. However, from the provided evidence alone, this is best characterized as missing enforcement of a newly implemented EIP rule rather than proof of an existing exploitable vulnerability.

## Walkthrough

1. `core/vm/evm.go` changes the `Create` path, which is the core contract-creation flow.

2. The pre-patch snippet shows caller nonce handling followed by progression to snapshot/account creation, with no visible collision check on the derived destination address.

3. The patch computes `contractAddr = crypto.CreateAddress(caller.Address(), nonce)` before snapshot/account creation.

4. It reads `StateDB.GetNonce(contractAddr)` and `StateDB.GetCodeHash(contractAddr)` to determine whether the destination is already occupied.

5. It introduces `emptyCodeHash = crypto.Keccak256Hash(nil)` so the code can distinguish an empty-code baseline from deployed code.

6. If the target nonce is non-zero or the code hash is neither zero nor `emptyCodeHash`, the function now returns `ErrContractAddressCollision`.

7. `core/vm/errors.go` adds that new error symbol so the rejection is explicit.

# Fix Pattern

Add an explicit precondition check in the CREATE path: derive the destination address early, inspect its occupancy state, and fail before account creation when the address is already in use.

## How It Was Fixed

The fix moves destination-address validation into `EVM.Create` itself. It adds `emptyCodeHash`, derives the target contract address before snapshot/account creation, checks the target nonce and code hash, and returns `ErrContractAddressCollision` when the address is already occupied instead of continuing the creation flow.

# Why It Matters

1. This affects a consensus-critical contract-creation path.

2. The patch enforces a concrete address-occupancy invariant instead of relying on later behavior.

3. The added error and guard make collision handling explicit and testable.

4. The evidence does not establish real-world exploitability or that prior behavior was invalid outside the new EIP rule.
