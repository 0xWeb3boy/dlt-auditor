# Summary

The patch separates signing setup from the node stack account manager and adds an `authorized` guard around Clique authorization during mining startup. That is consistent with hardening around wallet-endpoint disabling, but the provided evidence does not establish a concrete pre-patch vulnerability or a proven unauthorized signing path.

## Before/After Behavior

Before the patch, `NewServer` registered the keystore backend on `stack.AccountManager()` and `StartMining` entered the Clique authorization path without checking whether authorization had already happened. After the patch, `NewServer` creates a separate `accounts.Manager` for signing, later initialization uses `srv.backend`, and `StartMining` skips the authorization block when `s.authorized` is already true.

# Root Cause

The shown code mixed server-local signing setup with the node-wide account manager and did not explicitly track the case where consensus authorization had already been completed before `StartMining`. The evidence supports a design-tightening change, not a demonstrated exploit.

## Walkthrough

1. `internal/cli/server/server.go` creates the node stack and previously added a keystore backend directly to `stack.AccountManager()`.

2. The patch replaces that with a fresh `accounts.Manager` created only for this server-construction flow.

3. Related constructor calls are switched to `srv.backend`, including `ethstats.New(...)` and `StartMining(1)`, showing the new server-owned path is used consistently.

4. In `eth/backend.go`, `StartMining` gains an `if !s.authorized` guard around the Clique authorization logic.

5. The added comment ties that guard to the case where personal endpoints are disabled and authorization was already performed by the creating server.

# Fix Pattern

Separate privileged signing setup from the shared node account manager and add explicit state to avoid repeating authorization during miner startup.

## How It Was Fixed

`internal/cli/server/server.go` now creates a new account manager for signing instead of registering the keystore on `stack.AccountManager()`, and follow-on service wiring uses `srv.backend`. `eth/backend.go` now wraps the Clique authorization path in `if !s.authorized { ... }` so the server can pre-authorize consensus when personal endpoints are disabled.

# Why It Matters

1. It narrows where keystore-backed signing is wired into the server startup flow.

2. It preserves Clique validator startup after changing how signing is set up.

3. The diff does not show enough to prove prior unauthorized RPC reachability or key misuse.
