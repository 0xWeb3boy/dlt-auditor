## Before/After Behavior

Before the patch, `milestone.Lock` only rejected one existing-lock case and otherwise overwrote `LockedSprintNumber`; the shown `Unlock` form did not take an end-block hash. After the patch, `Lock` rejects locking at or below an existing whitelisted milestone, rejects backward relocking, purges milestone IDs and clears lock state on forward relocking, then records the new sprint number. `Unlock` now also stores `endBlockHash` in `LockedSprintHash`. The updated tests check chain-validation behavior after removing whitelist entries and then locking and unlocking against a concrete chain header and hash.

# Root Cause

The evidence points to incomplete milestone lock-state handling: the prior code did not fully enforce monotonic lock transitions and did not retain the associated end-block hash in the lock state.

## Walkthrough

1. `eth/downloader/whitelist/milestone.go` changes the `Lock` state-transition logic, which is the main substantive implementation change in the provided evidence.

2. The old `Lock` logic only handled one existing-lock comparison before overwriting `LockedSprintNumber`.

3. The new logic adds a guard against locking at or below an existing whitelisted milestone and separately rejects backward relocking.

4. On forward relocking, the code now purges milestone IDs and clears `Locked` before recording the new sprint number.

5. `Unlock` now takes `endBlockHash common.Hash` and stores it in `LockedSprintHash`, so the lock state contains both number and hash.

6. `eth/downloader/whitelist/service_test.go` was updated to create a lock from a real chain element, unlock with its hash, and then assert expected `IsValidChain` behavior.

7. The added Heimdall mock methods in `eth/handler_bor_test.go` are supporting test scaffolding, not direct evidence of the root issue.

# Fix Pattern

Tighten a local state machine by enforcing additional transition guards, clearing stale state on advancement, and storing the full state needed for later validation.

## How It Was Fixed

The patch hardens milestone lock bookkeeping. It prevents non-advancing or backward lock transitions relative to stored milestone state, clears old milestone ID state when advancing a lock, and records the locked sprint's end-block hash during unlock so later validation can use a more complete lock record.

# Why It Matters

1. Validation state is less likely to mix stale milestone metadata with a newer lock position.

2. Keeping the end-block hash makes the stored lock state more specific than a block number alone.

3. The tests show intended behavior changed in whitelist-based chain validation, but they do not prove an exploitable security flaw.
