## Code Shape Summary

- The strongest supported finding is a real integrity-check fix in the peer-facing chunk store path. Incoming chunk data is now hashed and compared with the advertised chunk key before acceptance, and related storage changes add fuller cleanup for already-corrupt local entries. Root cause: Incoming chunk payloads were not consistently validated against their content-addressed key in the peer-facing store path before being accepted into local chunk handling. A secondary storage issue was incomplete cleanup when a persisted chunk failed the same integrity check.

## Search Motifs

- state or trie data is loaded from disk or peer response without recomputing the expected root/hash
- path or key material from an external source reaches storage lookup/write before normalization
- missing mismatch handling lets corrupt or stale state be treated as canonical

## Typical Asymmetry

- Attacker-controlled data crosses remote peer to node networking boundary and reaches peer table mutation, sync scheduling, or message acceptance before the missing property is enforced.

## Patch Pattern

- Add explicit content-address validation on untrusted ingress, then use coordinated deletion and cleanup tooling for previously persisted inconsistent state.

## False Match Warnings

- Do not flag if the value is produced only by trusted local code and cannot be influenced across a protocol, RPC, or persistence boundary.
- Do not treat as exploitable if an earlier mandatory validation step rejects the malformed input before the sensitive sink.
- Consensus findings need evidence that different valid-looking inputs or node versions can reach divergent acceptance, state, or fork-choice behavior.
