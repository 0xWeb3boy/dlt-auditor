## Code Shape Summary

- The patch adds an explicit destination-occupancy check to EVM.Create and returns ErrContractAddressCollision when the derived contract address is already in use. That is security-relevant protocol validation logic, but the provided evidence supports this more as implementation of Metropolis EIP-684 than as a demonstrated vulnerability fix for previously incorrect behavior in the applicable ruleset. Root cause: The shown pre-patch Create path lacked a destination-address occupancy check before continuing with contract creation. However, from the provided evidence alone, this is best characterized as missing enforcement of a newly implemented EIP rule rather than proof of an existing exploitable vulnerability.

## Search Motifs

- state or trie data is loaded from disk or peer response without recomputing the expected root/hash
- path or key material from an external source reaches storage lookup/write before normalization
- missing mismatch handling lets corrupt or stale state be treated as canonical

## Typical Asymmetry

- Attacker-controlled data crosses persisted or peer-supplied state data to trusted local database boundary and reaches state commitment, canonical database write, or integrity decision before the missing property is enforced.

## Patch Pattern

- Add an explicit precondition check in the CREATE path: derive the destination address early, inspect its occupancy state, and fail before account creation when the address is already in use.

## False Match Warnings

- Do not flag if the value is produced only by trusted local code and cannot be influenced across a protocol, RPC, or persistence boundary.
- Do not treat as exploitable if an earlier mandatory validation step rejects the malformed input before the sensitive sink.
- Consensus findings need evidence that different valid-looking inputs or node versions can reach divergent acceptance, state, or fork-choice behavior.
