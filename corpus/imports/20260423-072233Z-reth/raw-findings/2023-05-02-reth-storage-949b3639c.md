# Summary

The patch changes beacon-engine forkchoice error handling so canonicalization failures are no longer handled only by logging and scheduling pipeline sync. It adds invalid-header tracking and an invalid-ancestor check before deciding how to respond. That is protocol-relevant behavior, but the provided evidence does not establish a concrete vulnerability beyond incorrect handling of known-invalid ancestry.

## Before/After Behavior

Before the patch, a `make_canonical` failure in `on_forkchoice_updated` stayed in an inline branch that logged the error, chose `PipelineTarget::Safe` or `PipelineTarget::Head`, and called `require_pipeline_run(target)`. After the patch, that failure path is delegated to `on_failed_canonical_forkchoice_update`, and new helpers `load_header`, `check_invalid_ancestor`, and `InvalidHeaderCache` support special handling for heads tied to previously tracked invalid headers instead of always falling back to sync recovery.

# Root Cause

The pre-fix forkchoice failure path treated canonicalization errors too generically. Based on the added invalid-header cache and ancestor check, the missing behavior was retention and reuse of invalid ancestry information when later forkchoice updates referenced the same invalid head or its descendants.

## Walkthrough

1. `on_forkchoice_updated` receives a `ForkchoiceState` and calls `blockchain_tree.make_canonical(&state.head_block_hash)` in the normal path.

2. The removed inline `Err(error)` branch only logged the canonicalization error, picked a pipeline target, and requested a pipeline run.

3. The patch replaces that inline recovery block with `self.on_failed_canonical_forkchoice_update(&state, error, is_first_forkchoice)`, showing the failure path now has dedicated logic.

4. New code adds `load_header` and `check_invalid_ancestor(head)`, and the latter starts by looking up the requested head in `self.invalid_headers` and deriving parent information from the cached header.

5. The file also adds `InvalidHeaderCache { headers: LruMap<H256, Header> }`, which is direct evidence that invalid-header state is now retained across requests.

6. Taken together, the shown change is that failed canonicalization can now consult tracked invalid ancestry before deciding whether to return an invalid-style result or continue with pipeline recovery.

# Fix Pattern

Separate known-invalid state from generic error recovery by caching invalid items and consulting that cache at the failure boundary.

## How It Was Fixed

The patch extracted canonicalization-failure handling into a dedicated helper, added support code to load headers and check invalid ancestry, and introduced an LRU cache of invalid headers keyed by hash. This lets the forkchoice path recognize previously known invalid ancestry instead of always treating canonicalization failure as a sync problem.

# Why It Matters

1. Forkchoice status handling is part of consensus-engine behavior, so misclassifying known-invalid ancestry can produce incorrect protocol-visible responses.

2. Remembering invalid ancestry across requests avoids losing earlier invalidity conclusions when the same head is seen again.

3. The evidence supports a correctness or hardening change in a sensitive path, but not a proven exploit or consensus break.
