## Before/After Behavior

Before the patch, the `attrs` path in `forkchoice_updated` could proceed without the newly shown consistency check, and the later status path could return a VALID-style response without the new `ensure_consistent_state_with_status(...)` guard. After the patch, the engine checks consistency before payload-attribute handling and again before returning success, and it returns an invalid response when the forkchoice state is inconsistent.

# Root Cause

Consistency validation for forkchoice state was not enforced at all of the relevant return and side-effect points. In particular, the payload-attributes path could bypass the new checks, and a computed status could be returned without confirming the forkchoice state matched canonical engine state.

## Walkthrough

1. `forkchoice_updated` processes a new forkchoice state and reaches the `make_canonical(&state.head_block_hash)` path.

2. In the `attrs` branch, the patch adds `ensure_consistent_state(state)?` before payload-attribute processing and returns an invalid response if the state is inconsistent.

3. Later in the flow, the old unconditional VALID-style return is replaced by `ensure_consistent_state_with_status(state, &status)?`, which blocks returning success for inconsistent state.

4. `update_canon_chain(...)` is changed to explicitly update head, finalized, and safe state through separate helper calls.

5. `BlockchainTreeViewer` gains `is_canonical(...)`, which appears to support the added consistency validation logic.

# Fix Pattern

Add explicit invariant checks at the boundary before side effects and before returning success, using canonical-state queries to validate the supplied forkchoice state.

## How It Was Fixed

The engine now performs consistency validation in two places: before processing payload attributes and before returning a successful forkchoice result. Supporting changes make canonical-state updates explicit and add a canonicality lookup helper used by the validation path.

# Why It Matters

1. It prevents the engine from acting on forkchoice state that does not match its canonical view.

2. It closes an early-return path that otherwise skipped the new consistency validation.

3. It improves protocol-correctness handling in a consensus-critical code path.

4. The provided evidence does not show exploitability, only that stricter validation was added.
