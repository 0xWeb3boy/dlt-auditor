## Before/After Behavior

Before the patch, storage proof dispatch only forced min_len(0) for storage targets associated with account-proof requests, empty subtries could fall through to an empty retained-proof result when retain_root was false, and pruning did not clear per-trie revealed_paths even though nodes were converted back to hash stubs. After the patch, all storage target sets force min_len(0) on the first target, empty subtries explicitly retain TrieNode::EmptyRoot, and pruning clears revealed_paths so later proofs re-reveal nodes from current trie state.

# Root Cause

The direct root cause shown by the snippets is inconsistent proof-generation and cache-invalidation behavior around empty storage subtries and pruned sparse tries. Root or empty-root evidence was not consistently preserved for all storage proof requests, and reveal metadata could remain after pruning changed the underlying trie representation.

## Walkthrough

1. In crates/trie/parallel/src/proof_task.rs, the code stops restricting min_len(0) to storage targets that overlap account targets and instead applies it to all storage target sets.

2. The new comment states why: storage-root computation needs the root, and storage-only targets need root-level nodes to prove non-existence when the subtrie is empty.

3. In crates/trie/trie/src/proof_v2/mod.rs, the former broad (false, _) branch is split so the empty-subtrie case (false, None) now pushes a ProofTrieNode with TrieNode::EmptyRoot.

6. The nearby prune documentation also records reveal-path clearing as part of pruning behavior, reinforcing that this is proof-state bookkeeping rather than a standalone security check.

# Fix Pattern

Return explicit root or EmptyRoot proof material for empty/non-existent storage subtries and invalidate proof-generation caches when pruning changes trie node representation.

## How It Was Fixed

The fix broadens root-node retrieval for storage proofs, preserves an explicit EmptyRoot node for empty subtries even when retain_root is false, and clears stale revealed_paths after pruning so subsequent proofs are rebuilt against the post-prune trie state.

# Why It Matters

1. Empty or non-existent subtries should not be represented by an ambiguous empty proof result.

2. Storage-only proof requests need the same root-level handling as account-associated storage proofs.

3. Pruning changes trie shape, so cached reveal metadata must be invalidated afterward.

4. The evidence shows proof correctness hardening, not a demonstrated verifier or consensus break.
