# Prompt: Base Hunter

Use this after `00_protocol_mapper.md` and together with one family prompt from `prompts/`.

## Objective

Find candidate issues of the requested family in the current blockchain or DLT codebase.

## Prompt

```text
You are hunting for one specific family of security issues in a blockchain or DLT codebase.

Inputs you already have:
- A protocol map of the system.
- One issue-family prompt describing what to look for.

Your task:
1. Enumerate the most relevant code paths for that family.
2. Search for places where the intended invariant is checked in some paths but missing in others.
3. Compare admission-time checks, execution-time checks, simulation paths, recovery paths, timeout paths, cleanup paths, and upgrade or migration paths where relevant.
3a. For transaction, block, message, and proof admission, build an ingress-to-sink matrix. For each object type, list every path that can place it into the shared sink: RPC, gossip, local builder, forced/internal insertion, replay/recovery, block packing, manager verification, and block verification. Mark which paths are trusted bypasses and which are untrusted. Every untrusted path should run the same policy, resource, context, and protocol-message checks before the object reaches the shared sink.
3b. For each security-sensitive object type, build an ingress-equivalence matrix across direct network receipt, local construction, preverification, canonical admission, replay, recovery, repair, simulation, compatibility, and version-specific parser paths. Mark the canonical validator and list every field, flag, feature gate, size/count bound, and helper-cache index domain that must be identical before the shared sink.
4. Identify suspicious asymmetries, TODO-style comments, placeholder checks, broad membership checks, stale state reuse, or checks performed too late.
5. Search for decisions that rely on cached, mirrored, or locally configured state instead of revalidating against authoritative chain or contract state at the point of use.
6. Search for policies enforced in signal, watcher, helper, or builder code but not in the provider, constructor, execution path, or storage write path that actually consumes the data.
7. Search for decisions keyed by one protocol coordinate, index, root, nonce, height, or game state while the code validates a broader aggregate, a proxy, or the first mismatch.
8. Produce at most 5 candidate findings, ranked by likelihood.
9. Search for the same semantic value carried in two or more representations, where only one representation is validated, canonicalized, or trusted.
10. Search compatibility, migration, mode-specific, and legacy branches for weaker hashing, version derivation, source selection, or verification behavior than the main path.
11. Search for sinks that should recompute an identifier, hash, version, capability, or selector from authoritative parsed state, but instead trust a detached field, helper output, cache entry, proof-carried value, or caller-supplied metadata.
12. Compare every special-case, compatibility, replay, migration, benchmark, recovery, sidechain, and fork-specific path against the normal validation path. Ask whether it skips only the exact non-comparable field or accidentally skips core identity, parent, root, accounting, authorization, or policy checks.
13. Search for feedback loops where untrusted peer, transaction, or proof outcomes should update reputation, penalties, scheduling, listener filtering, cache invalidation, or cleanup state. Check whether success, empty, invalid, timeout, abort, and retry paths update that state symmetrically.
14. Search for cached execution, proof, or state-provider outputs that include invocation-local state. On cache hits, the code should rebind or reconstruct caller-local accounting, fork identity, verifier context, and authoritative state instead of cloning stale composite objects.
14a. Search cached validation artifacts that cross rule-version, fork, epoch, consensus-parameter, or feature-gate boundaries. A cached "checked" object should carry the exact rule context that produced it, and sinks should revalidate when the current context differs.
15. In peer-driven paths, compare identity checks against context checks. Ask whether the code validates only a hash, type, peer, or object ID, or also validates the expected parent, predecessor, request token, chain segment, fork context, or authoritative metadata that makes the response meaningful.
16. Search read-only, debug, witness, trace, simulation, and inspection flows that reuse normal execution, import, or persistence helpers. Check whether writes are disabled at the actual storage or canonical-state sink, not just by a wrapper flag.
17. Compare constructor and startup paths for security-sensitive dependencies against steady-state enforcement paths. Ask whether verifier, signer, runtime-artifact, tracker, or state-provider initialization can fail open, fall back to trust mode, or proceed with incomplete chain context.
18. For multi-stage pipelines, compare extraction, witness recording, validation, pruning, recovery, and live execution. Ask whether later stages assume a witness, accumulator, module root, finalized boundary, or sequence check that earlier stages only record best-effort or under a different progress predicate.
18a. For proof or circuit-backed transaction families, build a per-field comparison across transaction object, signed message, witness, public data, circuit constraints, and persisted state. Search for fields that are present in execution or public data but not constrained equal to the signed or committed representation.
19. Search for internally generated or cascaded work that should be grouped atomically with its parent operation, such as retryables, auto-redeems, generated proofs, queued privileged submissions, or background follow-on actions. Check whether failure, filtering, replay, or recovery drops only the child work while keeping the parent side effects.
20. Search for privileged queues or session-bound workers where admission uses one authorization or freshness source but dequeue, replay, or round-transition execution uses another, such as cached controller maps, helper summaries, or stale progress state.
20a. For internal service APIs, compare security objects that are constructed with the route tree or server builder that actually handles requests. Treat "validator exists nearby" as insufficient unless middleware, interceptors, or handlers are mounted on every sensitive route.
20b. For nonce, sequence, ticket, or replay-sensitive admission paths, compare committed-state checks against local pending, in-flight, reserved, or recently-used state. Ask whether local state is used only to reject stale or duplicate work, or whether it can accidentally widen a future acceptance window.
20c. For verifier, prevalidator, middleware, signer-scope, or policy objects, compare construction with actual route, stream, queue, or sink enforcement. Treat optional policy configuration as suspicious if disabling the policy also disables baseline validation.
21. For account-ledger systems, build a before/after accounting model for each transaction family: direct entries, generated entries, reserves, owner counts, fees, supply, shares, receipts, obligations, and invariant finalizers.
22. For delegated, granular, or feature-scoped authorization systems, compare the permission object to the exact executed transaction shape, asset or domain, receiver policy, and every generated side effect.
23. For proposal/validation consensus systems, map proposal identity, prior-ledger binding, transaction-set or payload ordering, validator or committee trust, quorum arithmetic, and wrong-ledger, catch-up, or round-transition modes before searching for missing checks.
24. Compare adapter entrypoints against their canonical native entrypoints. For every precompile, cross-runtime query helper, legacy RPC adapter, or compatibility transaction path, ask whether it reuses the same validation, address association, chain or replay domain, message type, and final sink as the native path.
24a. For precompiles, host functions, proxy bridges, and VM-to-native adapters, compare caller class, target class, selector family, and call mode. Treat "same address format" as insufficient: distinguish EOA, contract-with-code, precompile, delegated/proxy real account, and native account. Search for broad generic dispatch adapters, allow-all proxy types, selector checks that run after dispatch setup, and target filters that check code presence but not precompile membership or native policy.
25. Search for early side effects that are recorded before final admission or success: pending nonces, peer penalties, callback writes, accounting deltas, generated receipts, cached proposal blocks, and temporary store writes. Check whether every later rejection, timeout, panic, or failed acknowledgement rolls them back or avoids recording them until acceptance.
25a. For delayed-accounting pipelines, build a before/after model around the exact state that later admission reads. Accepted transactions, votes, spends, withdrawals, account locks, and generated obligations should reserve or mutate the authoritative accounting state before another equivalent object can pass a stale check.
26. In consensus and p2p lifecycles, compare the predicate that verifies an object with the predicate that later mutates state from it. A certificate, peer response, stream discriminator, or proposal that was not needed or verified for the current transition must not still drive stored state, emitted votes, or allocation.
26a. Search for independent validation results that are aggregated before a state mutation, vote, dead-marker, queue insertion, or success response. Classify whether the protocol requires all checks to pass or only one alternative to pass. Treat `any success`, `or`, first-success, nil-on-one-branch, and generic-error collapse as suspicious when the checks validate different required properties.
27. Search caller/callee contract edges, not just protocol invariants. Compare what helpers, parsers, VM syscalls, copy-back routines, and cryptographic decoders document as their required backing span, output-buffer size, ownership lifetime, and exact destination-length contract against what call sites actually provide.
28. Treat typed stack locals, missing sentinel bytes, escaped local metadata, fixed-capacity receive buffers, and post-execution memcpy or copy-back without exact length equality as high-signal candidates.
29. Search admission and finalization paths where a policy is enforced against one representation while the final state mutation consumes another. Compare input fields vs emitted outputs, serialized rejected effects vs recomputed execution effects, cached resource metadata vs live call graphs, and deployment metadata vs synthesized proof or verifier artifacts.
30. Search privileged proxy, gateway, and service APIs for fallback behavior. Unknown methods, routes, selectors, or operation names should fail closed unless explicitly allowlisted; blacklist filtering is high-signal when the upstream target exposes a broader surface.
31. For deterministic VM account creation, compare the address derivation and deployment path against every native module that can create or mutate the same account address before deployment. Check whether the deploy path assumes a VM-specific account type before writing code hash, bytecode, nonce, balance, or metadata.
32. For precompiles, host functions, and VM-to-native adapters, compare success, revert, returned-error, panic, and cache-context failure exits. Native or local gas/resource consumption should be charged back to the outer runtime on every exit path that performed work.
33. For native adapters that call back into a VM or contract runtime, trace state object ownership across saved/restored state pointers, nested execution caches, dirty-object maps, and final commit order. A restored older cache must not overwrite state changed by nested execution or native module calls.
34. For helper callbacks into arbitrary token or contract code, check whether the callback gas budget is derived from the current caller frame or a protocol rule such as 63/64. Hardcoded gas budgets are suspicious when recursive calls can repeatedly enter the helper path.
35. For token integrations, test the integration model against non-standard return data, false returns, empty success returns, fee-on-transfer deltas, rebasing balance changes, callbacks, and metadata failures. Compare requested amount, actual delivered amount, escrow delta, minted/burned supply, and final invariant checks.
36. For fee, refund, denomination, and gas accounting, build a unit matrix across transaction building, ante/admission validation, execution, internal calls, tracing, display, refunds, and finalization. Every conversion boundary should name its unit and use the same canonical representation at equivalent sinks.
37. For batched or multi-message wrappers, compare ante/admission nonce or sequence updates against execution-time nonce writes for normal calls, contract creation, failed messages, and later messages in the same outer transaction.
38. For read-only, simulation, trace, or RPC execution that borrows live keepers or state caches, verify both persistence isolation and resource-accounting determinism. Read-only execution should not leave shared mutable pointers, warmed cache objects, or gas-meter state that can affect later live execution.
39. For native account creation modules, do not limit the search to genesis or migration incumbents. Include user-reachable vesting, locked, module, clawback, smart-contract, or derived accounts that can occupy an address later used by deterministic VM deployment.
40. For every native balance mutator, build a mirror-sync table: send, multi-send, module send, mint, burn, escrow, staking, delegation, undelegation, rewards, slashing, and contract-triggered native messages. Mark which path updates any VM-facing balance mirror and which path intentionally bypasses it.
41. For failed VM helper calls, build a four-column gas ledger: outer VM gas, native or SDK gas, helper-local gas, and caller refund. Compare success, revert, returned error, panic, and pre-validation failure. Do this separately for precompiles and internal contract-call helpers.
42. For nested StateDB or cache-context use, write a timeline of the active owner before the call, the owner during the nested call, the object dirtied by nested execution, the restored owner, and the final commit owner. Search for older owners overwriting newer object state.
43. For ERC20-style helpers, test optional-return compatibility exactly: empty successful return, one-byte or short return, ABI false return, revert, fee-on-transfer delta, balance change outside transfer, callback before balance snapshot, callback after balance snapshot, and metadata lookup failure.
44. For fee denomination and unit checks, compare local transaction builders and RPC constructors against `ValidateBasic`, ante decorators, fee deduction, execution gas pricing, refunds, and displayed/query fee fields. A builder using one unit can still be exploitable if admission accepts a different unit.
45. For multi-message wrappers, create a per-message timeline of account nonce, sequence, state-object nonce, fee gas, transient gas used, and refund base. Include a contract-creation first message followed by a normal call from the same sender.
46. For precompile or adapter method argument handling, list every decode, parse, address conversion, denom conversion, ABI unpack, and keeper lookup. If any error is ignored, trace the zero value or stale value to the first state, gas, or return-data sink.
47. For balance-outside-transfer tokens, compare snapshots taken before transfer, immediately after transfer, after callback, after rebase or external balance mutation, and during return/burn. Requested amount, received amount, escrowed amount, burned amount, and bank mirror amount should all reconcile.
48. For validation downgrades that cite an outer compensating control, require a second pass at the local invariant. A full outer gas burn, tx rollback, or query-only wrapper may not prove that local gas, cache ownership, mirror sync, nonce, or return-data invariants are safe.
49. For internal contract-call helpers, separate the callee runtime result from the caller accounting result. On every error exit, identify the `gasUsed` or remaining-gas value returned to the caller and the value the caller actually deducts, refunds, or persists.
50. For token helpers that claim ERC20 compatibility, treat empty successful return data as a distinct variant from ABI `false`. If the helper rejects an empty successful return, ask whether that is itself the compatibility/availability bug.
51. For fixed helper gas, check recursive and nested paths even when each individual helper call can revert. A fresh fixed budget on every nested call can create block-level work amplification or halt production without producing theft.
52. For multi-message nonce lifecycles, do not stop at ante sequence checks. Track SDK account sequence, EVM message nonce, in-memory StateDB nonce, contract-creation nonce reset, commit order, and later-message sender validation through the full wrapper.
53. For transaction fee denomination bugs, compare local builders, RPC builders, CLI builders, `ValidateBasic`, ante decorators, execution fee deduction, and final persisted fee/refund state. A builder/admission mismatch can be security-relevant even if trace/debug paths are also wrong.
54. For precompile balance or account query helpers, inspect each method body rather than only shared ABI decode. Look for ignored parser errors, shadowed `err` variables, default zero addresses, default denoms, and return construction after failed conversion.
55. For nested StateDB overwrite candidates, build the exact timeline for the outer Ethereum tx StateDB, any native adapter or precompile-saved StateDB, nested contract-call helper StateDB, restored pointer, and final dirty-object commit. Search for overwriting nested writes, not only stale mirror balances.
56. For trace/replay RPCs, bound every attacker-controlled work dimension independently: predecessor count, predecessor gas, traced tx gas, total trace timeout, trace output size, memory/stack capture, return data capture, and malformed nested tx validation.
57. For deterministic VM deployment, include future factory children and later nonce-derived addresses. Check whether normal users can create native vesting, locked, named, derived, or module-like accounts at those future addresses before deployment.
58. For account preemption, separate "new missing account default type" from "pre-existing account type." Deployment metadata, code hash, nonce, and balance writes must be checked against every pre-existing native account class.
59. For transaction fee unit bugs, trace fee amount provenance from signed VM fee helpers through builders, static validation, ante, fee deduction, execution, and refunds. Do not substitute value-transfer or trace-unit mismatches for the accepted-transaction fee sink.
60. For read-only shared-state residue, compare a node that served an estimate/query/trace/static call with a node that did not. Shared keeper fields, cache owners, warmed state objects, and gas-meter branches must be restored or irrelevant to later live execution.
61. For failed precompile/host-function gas, place every error return after native work on a timeline relative to local gas chargeback. A local gas mismatch can remain even when the outer transaction fails or rolls back.
62. For nested contract-call overwrite, identify the exact account or storage object dirtied before the helper, changed by the helper, and later committed by the older owner. Do not stop at generic "StateDB is shared" language.
63. For failed helper-call gas after prior work, compare the accounting branch used by successful helpers with the branch used by VM revert, returned error, panic, and pre-validation failure. Include prior helper work in the same outer transaction.
64. When a candidate is killed by a nearby control, write the exact property the control protects. If the missed property is different, keep a narrowed candidate instead of downgrading the whole class.
65. For regression-retention, after each family scan list the high-confidence mechanisms it would be dangerous to drop during canonicalization: native/VM mirror minting, optional-return token compatibility, deterministic future-address preemption, multi-message nonce/gas, trace replay budgets, parser-error continuation, and balance-outside-transfer accounting. A later phase may kill them, but only with sink-level evidence.
66. For native module calls reachable from VM execution, build a state-supply ledger with four columns: native bank balance, VM mirror balance, module/account supply, and dirty StateDB commit delta. Include staking, delegation, undelegation, rewards, slashing, Wasm/native messages, module sends, mints, burns, and escrow.
67. For token-standard compatibility, treat empty successful return data as its own candidate class even if the helper has balance-delta checks. Ask whether arbitrary third-party tokens are in scope and whether rejecting an otherwise successful token permanently blocks conversion or mapping use.
68. For fee validation and building, separate compatibility/admission invariants from actual fee debit. A later fee deduction path that recomputes the correct amount does not automatically kill a builder, static-validation, auth-info, signature, or mempool compatibility bug.
69. For failed precompile gas, build an error-class table before accepting or killing: ordinary returned error, VM revert-style error, local SDK out-of-gas panic, pre-validation failure, post-work method error, caller-caught failure, and top-level transaction failure. Record which gas budget is consumed for each row.
70. For failed native-to-VM helper calls, track both cumulative outer transaction gas and the helper's own `GasUsed` on success, VM failure, returned error, and panic. A bug can be in either block/transaction gas accounting or user refund/debit accounting.
71. For nested StateDB overwrite, keep it distinct from generic stale pointer cleanup: the evidence must name an object whose old value, nested helper-updated value, and final committed value differ.
72. For Wasm-precompile staking or delegation paths, do not merge the issue into generic stale `StateDB` cleanup. Trace funded `execute` or `executeMulti`, Wasm `StakingMsg`, SDK staking `DelegateCoinsFromAccountToModule` / `UndelegateCoinsFromModuleToAccount`, missing bank sync hook, dirty VM mirror value, and final `SetAccBalance` mint/burn delta.
73. For VM-triggered native balance mirror candidates, a "future EVM invocation overwrites the global pointer" kill is not sufficient when the same active EVM transaction still has a dirty object that will be committed after the native module call. Build the within-transaction timeline first.
74. For ERC20 helper gas, split successful `commit=false` read helpers from failed helpers and successful `commit=true` mutation helpers. A failed-helper full-gas burn does not kill a successful read-only helper undercharge.
75. For hardcoded helper gas recursion, prove whether each nested helper receives a fresh fixed helper gas cap rather than a budget derived from the parent frame. Treat block-level work amplification or production halt as an availability impact even without theft or persistent state corruption.
76. For every regression survivor class, preserve at least one exact candidate dossier when the scan has a concrete path for: Wasm staking mirror minting, fixed ERC20 helper gas, optional-return ERC20s, fee denomination in builders/static validation, deterministic account preemption, multi-message nonce/gas, trace replay, parser-error continuation, and balance-outside-transfer accounting.
77. For shared singleton keeper fields such as `Bank.StateDB`, build a two-validator determinism timeline. Validator A serves a read-only RPC/query/estimate/trace that installs or warms the shared pointer; validator B does not. Then compare the next consensus transaction's branch choices, cache hits, bank mirror sync calls, and gas consumed.
78. For read-only shared-state residue, distinguish persistence safety from consensus gas determinism. A query that commits no state can still be unsafe if it changes later live gas through a shared pointer, warmed cache, dirty-object map, or mirror-sync branch.
79. For outer `ethereumTx` versus nested `CallContract` ownership, name the outer StateDB, the nested StateDB, the object value before the helper, the nested-updated value, and the final value committed by the outer owner. Search for account balance, nonce, code hash, storage, and bank mirror overwrites.
80. For failed `CallContractWithInput` or internal helper calls, record the helper response gas used, the remaining gas, the caller's deducted gas, the block/transaction gas accumulator, and refund basis. Compare success, revert, returned error, panic, and SDK out-of-gas.
81. For failed precompile methods, do not accept "the EVM burns forwarded child gas" as a complete kill until the analysis proves the same repeated native SDK work is covered by that burned gas and cannot be retried or caught in a loop with fresh local/native budgets.
82. For the remaining partial classes, require a concrete named sink before canonicalization finishes: read-only shared-StateDB gas divergence, method-level failed-precompile native gas chargeback, outer-transaction StateDB overwrite of nested `CallContract` results, and failed `CallContractWithInput` gas-used mismatch.

For each candidate include:
- Title
- File and function
- What invariant seems intended
- Why the current path may violate it
- Attacker preconditions
- Possible impact
- What evidence would confirm or kill the hypothesis

Constraints:
- Do not claim a vulnerability just because a similar historical bug existed elsewhere.
- Prefer concrete code-level reasoning over speculation.
- Treat cryptographic validity, authorization, freshness, replay protection, version gating, and resource metering as separate properties.
- If no solid candidates exist, say so clearly.
```
